# Analytics foundation (collection disabled)

`LS_ANALYTICS_ENABLED=0` is the default. No business analytics events are wired into the UI. The optional collector and `/api/v1/analytics/events` interface are prepared for Phase 11, not activated. No orders, inventory, reviews, promotions, or purchases are implemented.

Schema version 1 allows `cafe_view`, `menu_view`, `product_view`, `favorite_add`, `directions_click`, `promotion_view`, and `out_of_stock_view`. Each batch has one cafe ID, 1–32 events, and a 16 KiB actual-body cap. Events contain only a generated event ID, type and UTC timestamp (within 24 hours, no more than 60 seconds ahead). Unknown fields, visitor identities, arbitrary payloads and purchase events are rejected. Twenty batches/IP/minute and 1,000 new events/cafe/day are initial optional-work caps; public event counts are not fraud-proof even with these controls. The cafe must currently be active. No IP or session identifier is persisted with analytics.

Browser collection is opt-in, bounded to 128 pending events, batched after five seconds, retried at most once after a failed send, and cleared on stop. Pending browser memory is lost on page/process closure or after retry exhaustion. This is deliberate optional analytics loss, not durable sensor telemetry behavior. Repeated sends reuse event IDs. There is no stable visitor ID or browsing-history table, and no unique-visitor estimate is invented.

A stable SQLite AnalyticsAggregator DO per cafe transactionally stores event receipts and increments hour/type counters before returning acceptance. In-memory counters are not authoritative. Duplicate event IDs do not increment counts; changed type/hour for an existing ID is rejected. Failed batches roll back. Receipts expire after two days, longer than the accepted event timestamp window. A 15-minute alarm, not a permanent timer, flushes at most 20 dirty summaries at once. Idle maintenance handles bounded receipt/counter retention.

D1 stores only `analytics_hourly(cafe_id,hour,event_type,event_count,revision,updated_at)`. A flush sends absolute cumulative counters with monotonic revisions. Repeated/ambiguous flushes cannot add a delta twice. Local dirty flags clear only after D1 success and only for the same revision; concurrent increments remain dirty. D1 quota failures postpone optional flushes for one hour; other failures retry after 15 minutes. Disabling collection stops optional alarm work but retains pending durable counters. Re-enabling collection/new intake schedules recovery. Never prioritize analytics retries over telemetry.

Future owner/admin read interfaces return bounded hourly or daily event summaries, authorize current role and cafe ownership, and explicitly report `uniqueVisitors: null`. UTC is the storage/aggregation boundary; future UI calendars must use Asia/Ulaanbaatar and clearly distinguish local days from UTC grouping. No event count is a physical visit, purchase, revenue total or calibrated sensor statistic. Owners cannot read raw receipt IDs or individual histories.

Cost model includes receipt/index writes, counter updates, per-batch intake budget writes, alarm rows, dirty-flag writes, retention deletes and idempotent D1 UPSERT/index writes. Default-disabled collection consumes none of those operations. Local tests cover transaction rollback, restart/reinitialization, deduplication and ambiguous D1 response retry. Optional loss boundaries: before a browser batch reaches the server, after bounded client retry exhaustion, explicit operator deletion or irrecoverable platform storage loss. Accepted DO counters survive normal hibernation/restarts and remain pending during D1 failures.
