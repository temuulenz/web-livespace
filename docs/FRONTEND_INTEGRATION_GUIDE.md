# Phase 11 frontend integration — A–H

No frontend implementation was changed. Existing uncommitted teammate frontend work remains untouched.

1. Authenticate through existing `/api/v1/auth/login` with JSON email/password; send cookies on same-origin API calls. Session revocation continues to work. Obtain an existing owned cafe ID; client-supplied ownership is never accepted.
2. Fetch `/api/v1/owner/cafes/{cafe}/menu/categories`, products and variants independently. Use bounded pagination and versioned PATCH. On 409 retrieve the entity again and let the user resolve conflicting edits.
3. Categories/products start as drafts. Create a category, then product with its category_id. Optional variants reference product_id. Publish both category and product for public visibility. DELETE product archives it and preserves its stable ID; DELETE variant deactivates it. Category deletion requires moving all products first.
4. Render published menu from `/api/v1/cafes/{cafe}/menu`; product details use product_id query. Featured/category/search filters are documented in MENU_MANAGEMENT.md. No homepage-wide menu request is needed. Flags on returned entities are 0/1. Prices are integer MNT; discounted_price may be null. Empty variants means a product without variants.
5. Use PUT product image with current version and a validated data URL, then use product image URL for retrieval. Images support ETags. Replacing or detaching updates product version. Do not reuse stale versions.
6. CSV imports require preview, explicit user confirmation, and identical CSV + preview_id + confirm:true. Imported products stay drafts. Limit 20 rows; bulk edits limit ten entities.
7. Render stored strings as text, never innerHTML. Do not infer stock status from menu publication. Inventory, reviews, promotions and private aggregate APIs are implemented. See the current contracts linked below.

Prose contract: MENU_MANAGEMENT.md. Machine contract: openapi.yaml. Postman-compatible collection: PHASE11.postman_collection.json. Local isolated demonstration: `node scripts/phase11-menu-demo.mjs`; it creates an ephemeral server/database/files, exercises APIs, prints simulated menu JSON and cleans up. It does not leave a listening server or reusable login session.

No menu realtime events currently exist. Following a successful owner mutation, refetch that cafe's affected menu data. Existing sensor realtime flows do not imply inventory availability. Public server snapshots cache for five seconds and mutations invalidate only affected cafe snapshots; HTTP responses remain no-store.
