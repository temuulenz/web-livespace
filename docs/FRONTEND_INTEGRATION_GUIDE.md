# Phase 11 frontend integration checkpoint

No frontend implementation was changed. Existing uncommitted teammate frontend work remains untouched.

1. Authenticate through existing `/api/v1/auth/login` with JSON email/password; send cookies on same-origin API calls. Session revocation continues to work. Obtain an existing owned cafe ID; client-supplied ownership is never accepted.
2. Fetch `/api/v1/owner/cafes/{cafe}/menu/categories`, products and variants independently. Use bounded pagination and versioned PATCH. On 409 retrieve the entity again and let the user resolve conflicting edits.
3. Categories/products start as drafts. Create a category, then product with its category_id. Optional variants reference product_id. Publish both category and product for public visibility. DELETE product archives it and preserves its stable ID; DELETE variant deactivates it. Category deletion requires moving all products first.
4. Render published menu from `/api/v1/cafes/{cafe}/menu`; product details use product_id query. Featured/category/search filters are documented in MENU_MANAGEMENT.md. No homepage-wide menu request is needed. Flags on returned entities are 0/1. Prices are integer MNT; discounted_price may be null. Empty variants means a product without variants.
5. Use PUT product image with current version and a validated data URL, then use product image URL for retrieval. Images support ETags. Replacing or detaching updates product version. Do not reuse stale versions.
6. CSV imports require preview, explicit user confirmation, and identical CSV + preview_id + confirm:true. Imported products stay drafts. Limit 20 rows; bulk edits limit ten entities.
7. Render stored strings as text, never innerHTML. Do not infer stock status from menu publication. Inventory and reviews are now implemented; promotions/statistical APIs remain absent. See the current contracts linked below.

Prose contract: MENU_MANAGEMENT.md. Machine contract: openapi.yaml. Postman-compatible collection: PHASE11.postman_collection.json. Local isolated demonstration: `node scripts/phase11-menu-demo.mjs`; it creates an ephemeral server/database/files, exercises APIs, prints simulated menu JSON and cleans up. It does not leave a listening server or reusable login session.

No menu realtime events currently exist. Following a successful owner mutation, refetch that cafe's affected menu data. Existing sensor realtime flows do not imply inventory availability. Public server snapshots cache for five seconds and mutations invalidate only affected cafe snapshots; HTTP responses remain no-store.

Inventory integration (11B): retrieve the separately paginated `/api/v1/cafes/{cafe}/inventory` snapshot and merge by product_id+nullable variant_id into visible menu products. Missing inventory is unconfigured, not zero. Apply inventory.changed only when per-target version increases; recover gaps/reconnect using snapshot_url. Cloudflare live.snapshot now contains inventory revision/recovery URL. Node has a dedicated cafe inventory SSE endpoint. Never infer quantity from status or expose hidden owner quantities. For owner edits use current version, unique idempotency_key and 1–5 updates; retry the identical request on ambiguous network failures. Full JSON/errors/cache/event contract: INVENTORY_MANAGEMENT.md. No frontend handlers were changed.

Reviews (11C): use the five keys taste,service,comfort,value,study (integers 1–5), optional plain comment, and the current positive review version for edits/deletion. GET /me/cafes/{cafe}/review recovers the current author record after ambiguous creation. Creation retry may return review_exists. Owner reply creation uses version 0, subsequent edits/deletion current reply version. Owners can report a review and reply; only admins may moderate it. RATINGS_AND_REVIEWS.md specifies all routes, projections, null/no-review summaries and distributions. Render comments/names/replies as text, never HTML. No verified-visitor badge or business conclusion is supported. Public inventory deltas replace each target's projection: if quantity is omitted, remove any previously displayed quantity. No production UI/event handlers were changed.

Reviews integration (11C): use GET public /cafes/{cafe}/reviews and /ratings independently. POST requires all five criterion keys; author GET /me/cafes/{cafe}/review recovers state after a network failure. PATCH/DELETE require current review version. Owner replies use version 0 for creation/current version for edit/delete. Owner reporting never hides a review; moderation is admin only and reasons are mandatory. Summaries return null averages for no reviews, thirty explicit distribution bins, and no verified-visit claim. Full requests/responses/errors: RATINGS_AND_REVIEWS.md. Review notifications await 11G. The machine contract now contains 45 operations (menus/inventory/reviews); the collection has 46 requests with existing login.

The isolated demonstration command now exercises menu, stock and a clearly simulated review/rating in an ephemeral cafe marked data_mode=demo; no real customer feedback or production records are inserted. All local fixture users/files/database are removed on completion. Research aggregate export endpoints remain a future 11F task. Public review/rating responses are operational summaries, not business conclusions.

11D additions: PROMOTION_ENGINE.md documents owner configuration/preview, public active retrieval, informational-only types, UTC envelopes and Asia/Ulaanbaatar recurrence. Current listed menu price comes from DB; preview requests never include client prices. Overlapping rules do not stack. Handle 409 access_changed by reloading/re-authenticating; transaction-time session/ownership changes no longer commit stale writes. GET /api/v1/ready is for operators, not a replacement for discovery data or evidence of production readiness. No UI/event handlers changed.
