# First-client pilot preparation — not launch approval

Controlled remote pilot remains NO-GO until the blockers/action list is satisfied. No client identity, venue data, phone accuracy, calibration, support address or consent policy has been invented. Local synthetic demonstrations are available.

1. Owner supplies actual venue name/contact/address, supported category (Кафе/Коворкинг/Номын сан), district, coordinates, hours, description, purposes, seats and permitted photos. Use existing POST /api/v1/applications; the parser requires 3–4 valid raster photos. Do not invent accessibility/amenity fields absent from the contract.
2. Use returned one-time claim_token with POST /api/v1/auth/register-owner or authenticated /api/v1/applications/claim. Never log/share claim tokens. Competing claims must have a single winner; a failed registration/claim may leave a registered account, so recover by login rather than assuming identity deletion. Owner/admin cannot arbitrarily claim another cafe.
3. Admin follows documented submitted → review/contact/visualization/sensors/testing → active workflow. A live cafe requires map location before activation. Preserve current publication rules and inspect public data before approval.
4. Owner configures menu/categories/products/variants, stock source/visibility, and optional promotion rules through feature-guide APIs. Frontend business integration remains teammate work. No orders/payment flows exist.
5. Admin registers physical sensor via /api/v1/admin/devices, separate from simulator. Transfer the one-time bearer privately; use frozen SENSOR_PROTOCOL.md. Production requires WSS, normal certificate checks and network reachability. Disabling/revoking/replacing credentials must be rehearsed in isolation before actual device changes.
6. On the actual phone/network, verify UTC timestamps, device/location IDs, durable ACK/outbox replay, reconnect, duplicates, ordering, stale/offline/recovery. People count is not seat availability; uncalibrated dBFS is not SPL. Do not manufacture live data to hide gaps. Camera/audio processing stays on-device; no raw recordings, faces or visitor identities enter the protocol.
7. Confirm provider schema/bindings/cadence/headroom, reviewed backup+recovery, monitoring and support contacts before publication. Owner decides retention and disclosure with appropriate review; this document asserts no legal compliance. Inventory receipts/review audits/sensor dedupe identities require correctness-preserving retention, not blind deletion.
8. Pilot exit criteria require agreed data-quality/availability targets, verified owner isolation, accurate real venue data, observed device recovery, support response process and reviewed failure/rollback evidence. These targets are owner/client decisions, not invented business acceptance criteria.
